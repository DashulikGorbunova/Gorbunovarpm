# 1. Вспоминаем архитектуру

После шардирования путь запроса выглядит так:

```
                        Backend (Django / DRF)
                               │
                        ShardRouter (shop/sharding.py)
                 shard = ring(customer_id)   или  hash(customer_id) % N
                               │
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
   shop_order_shard        shop_order_shard       shop_order_shard
      shard0                  shard1                 shard2
    33 350 строк            33 766 строк           32 884 строк
        │                      │                      │
        └────────── результаты собираются в backend ──┘
                        (scatter-gather + merge)
```

**Router** решает, куда отправить запрос. Если shard key есть в `WHERE` — это **один** шард. Если нет — запрос рассылается по всем шардам (scatter), а результаты объединяются в приложении (gather/merge). Именно поэтому в лабе 5 мы выбрали shard key `customer_id`: он есть в самых частых запросах сервиса.

Сводка роутера (`GET /api/shards/distributed/?mode=summary`):

```
Router: strategy=consistent shards=3 vnodes=160 ring_points=480
Где объединяются результаты: backend (application layer)

Single-shard запросы:
  + GET /api/shards/route/?customer_id=?  -> WHERE customer_id = ?
  + GET /api/customers/{id}/orders/       -> WHERE customer_id = ?
  + GET /api/orders/?customer=?           -> WHERE customer_id = ?
Distributed запросы:
  - COUNT(*) / SUM() / GROUP BY по всем заказам
  - ORDER BY created_at DESC LIMIT n (глобальный топ)
  - JOIN заказов (шарды) с клиентами (Primary)
  - GET /api/orders/ (список без фильтра по клиенту)
```

# 2. Single-Shard Query

Запрос сервиса (список заказов клиента) — `GET /api/customers/{id}/orders/`:

```sql
SELECT id, customer_id, status, total_amount, created_at
FROM shop_order_shard
WHERE customer_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

`customer_id` — это shard key, поэтому роутер по хэшу ключа определяет **один** шард:

```
WHERE customer_id = 1  ->  shard2
Затронуто шардов: 1 (остальные не читаются)
Время: 37.293 ms, строк: 10
```

**Почему не нужно обращаться к другим шардам:** все строки одного `customer_id` живут на одном шарде — это гарантируется детерминированной функцией размещения (`shard = ring(customer_id)`). Значит, условие `WHERE customer_id = ?` может выполнить ровно один узел, а остальные два гарантированно не содержат подходящих строк. Поэтому:

- читается 1 шард вместо 3 (`shards_touched = 1`);
- нет scatter-gather, нет сетевой сборки результатов, нет дублей;
- время ответа не зависит от количества шардов — это ключевое свойство корректного shard key.

То же самое относится к `GET /api/orders/?customer=42` и к эндпоинту `/api/shards/route/?customer_id=`. Это «хорошие» запросы сервиса: их стоимость после шардирования **не выросла**, а упала, потому что каждый шард хранит лишь 1/3 данных (≈33k строк вместо 100k).

# 3. Агрегирующий запрос

Агрегация сервиса — `COUNT(*)` / `SUM(total_amount)` / `GROUP BY status` по заказам. После шардирования данные распределены, поэтому агрегат нужно считать **на каждом шарде и сложить**.

Реальный прогон (`python manage.py shard_queries`):

```
--- 3. Распределённая агрегация ---
COUNT(*) по шардам:
  shard0 = 33350,  shard1 = 33766,  shard2 = 32884
  merged COUNT(*) = 100000

SUM(total_amount) по шардам:
  shard0 = 166 383 936.28
  shard1 = 168 182 937.46
  shard2 = 164 758 736.32
  merged SUM = 499 325 610.06

GROUP BY status (по шардам -> merged):
  shard0: PROCESSING 8296, CANCELLED 4237, DELIVERED 8465, NEW 4131, PAID 8221
  shard1: CANCELLED 4241, PROCESSING 8587, DELIVERED 8385, NEW 4240, PAID 8313
  shard2: CANCELLED 4137, PROCESSING 8142, DELIVERED 8220, PAID 8175, NEW 4210
  merged:
    CANCELLED  12615
    DELIVERED  25070
    NEW        12581
    PAID       24709
    PROCESSING 25025
    (сумма = 100000)

  суммарно по шардам: 77.084 ms, максимум на одном шарде: 35.846 ms
```

Как это сделано (упрощённо, `shop/distributed.py`):

```python
# scatter: одинаковый агрегат на каждом шарде
SELECT status, count(*) FROM shop_order_shard GROUP BY status;

# gather/merge: сложить группы с одинаковым ключом
def merge_group_by(per_shard_rows, key, value):
    merged = {}
    for rows in per_shard_rows:
        for row in rows:
            merged[row[key]] = merged.get(row[key], 0) + row[value]
    return merged
```

**Ответы на вопросы:**

**1. Можно ли выполнить такой запрос только на одном shard?**  
Нет. Ни одно решение не гарантирует, что все строки, попадающие под условие, лежат на одном шарде. `COUNT(*)`, `SUM`, `GROUP BY` без фильтра по shard key обязаны пройти по **всем** шардам. Единственное исключение — если в `WHERE` есть shard key (`WHERE customer_id = 1 … GROUP BY status`): тогда агрегат считается на одном шарде.

**2. Где должны объединяться результаты?**  
В **backend**, на уровне приложения (router/сервисный слой). PostgreSQL не умеет объединять результаты из разных инстансов: каждая база считает только свой локальный агрегат, а слияние (сумма counts, сумма sums, объединение групп) делает код после scatter-gather. Ровно это видно в `merged COUNT(*) = 100000` (= 33350 + 33766 + 32884).

**3. Что происходит со временем выполнения при увеличении количества shard'ов?**  
Время одной **полной** агрегации примерно равно `max(время по шарду)`, а не сумме, если запросы идут параллельно; при последовательном выполнении — растёт линейно по числу шардов. Важно, что растёт и объём передаваемых данных и стоимость сборки в backend: каждая дополнительная группа/строка с шарда — это сетевой трафик и память приложения. Поэтому агрегацию «по всей базе» шардирование **не ускоряет**: шардов больше → запрос по-прежнему трогает все узлы. Зато размер данных на каждом узле меньше, и если бы все шарды опрашивались параллельно, суммарное время могло бы даже уменьшиться — но не в 3 раза, а ограничивается самым медленным шардом и сетью.

# 4. JOIN между shard'ами

JOIN сервиса — «заказ + клиент» (`GET /api/orders/with-details/`). После шардирования таблицы оказались на **разных** узлах:

```
   shard0/1/2 (шардированы)              Primary (не шардирован)
   shop_order_shard                      shop_customer
   customer_id  ──────  JOIN  ──────────  id
```

Реальный прогон показывает, что обычный SQL JOIN по одному узлу невозможен:

```
--- 4. Cross-shard JOIN ---
Заказы: shard2 (0.62 ms), клиент: default (Primary) (15.19 ms)
  shop_customer на shard0: relation "shop_customer" does not exist
  shop_customer на shard1: relation "shop_customer" does not exist
  shop_customer на shard2: relation "shop_customer" does not exist
  join выполнен в backend, строк: 5
```

Пришлось сделать так (join в приложении):

```python
orders   = SELECT ... FROM shop_order_shard WHERE customer_id = %s   # шард
customer = SELECT ... FROM shop_customer     WHERE id = %s           # Primary
joined   = [{**row, 'customer_name': customer['first_name'] + ' ' + ...} for row in orders]
```

**Ответы на вопросы:**

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?**  
Обычный `SELECT … FROM A JOIN B` становится невозможен: таблицы `A` и `B` физически на разных серверах, между ними нет общего SQL-контекста. Либо строки `B` надо доставить к `A` по сети, либо join выполнять в приложении (как мы и сделали), либо денормализовать данные.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?**  
Нет. Если `A` на shard2, а `B` на Primary, ни один инстанс не видит обе таблицы. `relation "shop_customer" does not exist` на всех шардах — это прямой и честный результат: локально join не собрать.

**3. Какие данные пришлось бы передавать между shard'ами?**  
Для join `order → customer` нужно либо передать на шард строку клиента (одну или пачкой для набора заказов), либо поднять с шарда набор заказов в backend и соединить там. В общем случае через сеть гоняется наименьшая из сторон join — но при JOIN нескольких больших таблиц объём может быть огромным, и это главная стоимость cross-shard JOIN.

**4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного shard'а?**  
Да — **ко-локация по общему ключу**. У нас shard key заказов — `customer_id`. Если **и клиентов шардировать тем же ключом** `customer_id` (одно и то же значение → один и тот же шард), то `shop_order_shard` и `shop_customer_shard` для конкретного клиента окажутся на одном узле, и `JOIN` станет **single-shard**. Это стандартный приём: связанные сущности шардируют по одному ключу (tenant_id / user_id). Тогда distributed остаются только join'ы сущностей, которые нельзя привязать к этому ключу.

# 5. ORDER BY + LIMIT

Запрос сервиса — «последние заказы» (`GET /api/orders/?ordering=-created_at`):

```sql
SELECT id, customer_id, status, total_amount, created_at
FROM shop_order_shard
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

После шардирования каждый узел знает только свой локальный топ. Реальный прогон:

```
--- 5. ORDER BY + LIMIT 20 ---
  shard0: top-1 id = 7403304 (33.015 ms)
  shard1: top-1 id = 7913212 (16.027 ms)
  shard2: top-1 id = 9000003 (14.432 ms)
  merged top-20: первые id = [9000003, 9000002, 9000001, 7913212, 7403304]
  max на шарде: 33.015 ms, суммарно: 63.473 ms
```

Схема:

```
shard0 -> top 20  (...7403304)
shard1 -> top 20  (...7913212)
shard2 -> top 20  (...9000003)
        ↓  backend: merge + sort + LIMIT 20
   глобальный top 20: 9000003, 9000002, 9000001, 7913212, 7403304, …
```

**Почему недостаточно получить первые 100 записей только с одного shard'а.**  
Потому что «самые новые» заказы распределены по всем трём шардам: каждый шард хранит заказы своих клиентов. Локальный top-100 одного shard'а — это не глобальный top-100: на другом шарде лежат записи новее. В нашем прогоне самый свежий заказ (`9000003`) оказался на shard2, а лучший на shard0 (`7403304`) — лишь 5-й в глобальном списке. Чтобы получить корректный глобальный топ, нужно:

1. запросить top-N на **каждом** шарде (`ORDER BY … LIMIT N` локально — быстро, работает индекс `(customer_id, created_at DESC)` / `created_at`);
2. собрать `N × shards` строк в backend;
3. отсортировать объединённый набор и взять первые N.

Только так ответ будет правильным. С каждого шарда достаточно взять ровно `N` строк (не больше) — это классический «N per shard» merge.

# 6. Отказ одного shard

Реальный эксперимент: остановили `shard2` (на нём живёт клиент 1) и обратились к сервису.

```
$ docker stop flower_shop_shard2

--- COUNT(*) при недоступном shard2 ---
merged = 67116, failed_shards = ['shard2']
per-shard: shard0 ok, shard1 ok, shard2 FAILED

--- GET /api/shards/route/?customer_id=1  (клиент на shard2) ---
{ "shard_alias": "shard2", "orders_count": 0,
  "error": "could not translate host name \"shard2\" to address: ..." }

--- GET /api/shards/route/?customer_id=3  (клиент на shard1) ---
{ "shard_alias": "shard1", "orders_count": 18, "error": null }

--- shard_report ---
rows: {'shard0': 33350, 'shard1': 33766}
errors: {'shard2': 'could not translate host name "shard2" ...'}

после `docker start flower_shop_shard2`:
merged = 100000, failed_shards = []
```

**Ответы:**

**1. Какие данные становятся недоступны?**  
Только строки, чей shard key (`customer_id`) отображается на упавший шард: у нас ≈32.9 % заказов (32 884 из 100 000) и примерно столько же клиентов (1 641). Данные остальных двух шардов (≈66 990 заказов) полностью доступны.

**2. Какие endpoint'ы перестанут работать?**  
Зависящие от упавшего шарда:
- `GET /api/shards/route/?customer_id=<на shard2>` — `error` (как выше);
- `GET /api/customers/{id}/orders/` и `GET /api/orders/?customer=<на shard2>` — те же клиенты;
- распределённые запросы (`COUNT/SUM/GROUP BY`, `/api/shards/distributed/?mode=count`, глобальный top) — **деградируют**: отдают неполный результат (`67116` вместо `100000`) и помечают `failed_shards`.

**3. Продолжит ли работать остальная часть сервиса?**  
Да. Клиенты на shard0/shard1 обслуживаются нормально (`customer_id = 3 → shard1, 18 заказов, error = null`). Каталог, товары, клиенты на Primary/Replica тоже работают. Отказ одного из N шардов «роняет» не весь сервис, а лишь 1/N данных — это плюс шардирования по сравнению с единой БД.

**4. Что должен делать backend при обращении к недоступному shard?**  
Не отдавать «тихую» пустоту (`orders_count = 0` без объяснения — плохо). Правильно:
- различать «данных нет» и «шард недоступен» — возвращать `503`/ошибку с явным признаком (`error`, `failed_shards`), как в распределённых запросах;
- ставить таймауты и circuit breaker, чтобы не ждать мёртвый узел;
- для частичных результатов (агрегации) явно помечать полноту (`partial: true`);
- иметь retry к реплике этого шарда, если она есть.

**5. Как можно повысить отказоустойчивость?**  
- **Реплика на каждый шард** (как в лабе 4): при отказе primary шарда чтение переключается на реплику;
- **автоматический failover** (Patroni/etcd, repmgr) — поднятие standby вместо упавшего;
- **больше шардов** → доля недоступных данных меньше;
- **backup + PITR** для восстановления;
- на уровне приложения — health-check шардов и корректная деградация: частичный ответ с явной пометкой, а не 500 и не пустой результат.

# 7. Hot Shard

Сценарий: `shard0 → 10 %`, `shard1 → 15 %`, `shard2 → 75 %` запросов. Проверим реально: 10 000 запросов, из которых 9 000 идут к самым «горячим» клиентам («популярный пользователь/tenant»), остальные — равномерно.

```
--- 7. Hot shard simulation ---
Запросов: 10000 (из них 9000 — к популярным клиентам)
Доля строк по шардам:    {'shard0': 33.35, 'shard1': 33.77, 'shard2': 32.88}
Доля запросов по шардам: {'shard0': 40.09, 'shard1': 21.32, 'shard2': 38.59}
Вердикт: hot shard

Топ-10 клиентов по числу заказов:
  customer 266  (38 заказов) -> shard2
  customer 4016 (36 заказов) -> shard1
  customer 3374 (35 заказов) -> shard2
  customer 4260 (35 заказов) -> shard2
  customer 4575 (35 заказов) -> shard0
  ...
```

Обратите внимание: **строки распределены идеально** (33.35 / 33.77 / 32.88), а **запросы** — уже нет (40 / 21 / 39). Тот же эффект, но сильнее, даст один «вирусный» клиент: его шард получит почти всю нагрузку.

**Возможные причины:**

- **неудачный shard key** — если бы ключом был, например, `status` или `created_at`, горячие значения собрали бы нагрузку на одном узле;
- **неравномерное распределение данных** — часть шардов заметно больше (у нас 33 350 против 32 884 — мелкая, но при плохом хеше может быть в разы);
- **популярный пользователь/tenant** — активный клиент всегда попадает на один и тот же шард (это цена ко-локации);
- **определённый тип запросов** — например, все запросы «новые заказы» (`status='NEW'`) сканируют все шарды, но если бы горячий статус встречался в основном на одном шарде, он бы «крутился» сильнее.

**Почему равное количество строк на шардах ещё не означает равномерную нагрузку?**  
Нагрузка определяется не количеством строк, а количеством и «весом» **запросов**. Три причины:

1. **Разный доступ к разным клиентам.** Один tenant может генерировать в десятки раз больше запросов, чем остальные, а он целиком лежит на одном шарде.
2. **Разные типы запросов.** Сканирующие запросы без shard key (`COALESCE`-агрегации, «все заказы за период») грузят **все** шарды, поэтому строки тут не при чём.
3. **Разная стоимость строк.** Заказ с длинными `comment`/`delivery_address` «тяжелее» при чтении, чем короткий; hot-данные могут чаще попадать в горячий кэш одного узла.

Поэтому shard key надо выбирать не только по «равномерности строк», но и по равномерности **доступа**. Если перекос по доступу неизбежен (горячий tenant), помогает разбиение такого tenant на отдельные шарды или отдельный «выделенный» узел.

# 8. Итоговый анализ shard key

**Выбранный shard key:** `shop_order.customer_id`.

## Плюсы — какие запросы стали эффективными

- `WHERE customer_id = ?` → **single-shard**: `GET /api/customers/{id}/orders/`, `GET /api/orders/?customer=`, `/api/shards/route/`. Трогается 1 шард из 3, время не растёт с числом шардов (37 ms у нас).
- Заказы одного клиента **ко-локализованы**, поэтому клиентские ленты, пагинация и сортировка внутри клиента выполняются локально и быстро (индекс `(customer_id, created_at DESC)` на шарде).
- Распределение данных равномерное: 33 350 / 33 766 / 32 884, отклонение 1.3 % (лаба 5).
- Ключ совпадает с естественной границей изоляции (tenant), поэтому `DROP`/архивация клиента — это операция в пределах шарда.

## Минусы — какие запросы стали распределёнными

- **Агрегации без фильтра по клиенту**: `COUNT(*)`, `SUM`, `GROUP BY status` — все три шарда + merge.
- **Глобальный ORDER BY + LIMIT** («последние заказы») — top-N с каждого шарда + merge.
- **JOIN с не-шардированными таблицами** (`shop_customer`, `shop_product`, `shop_orderitem`) — join в приложении, потому что таблицы на разных узлах.
- **Отчёты и «всё по всем клиентам»** — всегда scatter-gather.

## Проблемные операции (от самой сложной)

| Операция | Сложность | Почему |
|----------|-----------|--------|
| **JOIN** | высокая | Связанные таблицы на разных узлах; нужна ко-локация или join в приложении; в худшем случае — большой сетевой обмен |
| **aggregation** | высокая | Нужен merge в backend; `DISTINCT`/`COUNT(DISTINCT)` и точные средние — особенно неудобны (нельзя усреднять средние!) |
| **ORDER BY + LIMIT** | средняя | Обязателен top-N с каждого шарда; `OFFSET` вглубь списка становится очень дорогим |
| **migration (rebalancing)** | средняя | При `modulo` — почти всё переезжает (76 %); с consistent hashing — ~1/N; но сам перенос всё равно надо обеспечивать |
| **backup / восстановление** | средняя | Резервное копирование и PITR нужно делать по каждому шарду согласованно; полный restore — это N отдельных restore |
| **балансировка** | средняя | Нужны виртуальные узлы (`vnodes`) и перенос дуг; hot tenant остаётся проблемой |

## Вывод

**Оставил бы выбранный shard key — да, с одним улучшением.**  

`customer_id` подходит сервису: основной поток запросов — это «заказы клиента», и он выполняется на одном шарде; данные распределяются равномерно (1.3 %), а не «тяжело» мигрируют при добавлении узла (consistent hashing ≈ 25 % вместо 76 %).

Главное улучшение — **ко-локация клиентов**: шардировать `shop_customer` тем же ключом `customer_id`, чтобы `JOIN` «заказ ↔ клиент» из distributed превратился в single-shard. Также я бы:
- держал `shop_order_shard` денормализованно (уже так: `total_amount`, `status` прямо в заказе), чтобы каталог/позиции не требовали cross-shard join;
- остался на **Consistent Hashing** с виртуальными узлами;
- для «горячих» tenant закладывал выделенные шарды.

Другой ключ (например, `order.id`) я бы **не** выбирал: он даёт равные строки, но разрушает ко-локацию, и тогда даже «заказы клиента» станут distributed — сервис потерял бы свои основные быстрые запросы.

# Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?**  
Single-shard обращается к одному узлу: в `WHERE` есть shard key, и router доказывает, что остальные шарды не содержат нужных строк (`WHERE customer_id = 1`). Distributed требует опросить несколько (или все) шардов и собрать результат в backend: агрегации, глобальный `ORDER BY … LIMIT`, cross-shard JOIN. Single-shard масштабируется вместе с числом шардов (работает 1 узел), distributed — нет (работают все).

**2. Почему JOIN между shard'ами сложнее обычного JOIN?**  
В одном PostgreSQL планировщик видит обе таблицы, статистику и индексы, и может выбрать hash/merge join, читая данные с диска. Когда таблицы на разных серверах, единого плана нет: SQL-движок одного узла не видит вторую таблицу (у нас — `relation "shop_customer" does not exist`). Приходится передавать данные по сети и соединять в приложении, теряя оптимизации планировщика и получая сетевые задержки.

**3. Как выполнить COUNT(*) по всем shard'ам?**  
Разослать `SELECT count(*)` на каждый шард, получить локальные счётчики и сложить их в backend: `33 350 + 33 766 + 32 884 = 100 000`. Это работает только для «аддитивных» агрегатов (COUNT, SUM); `AVG` надо считать как `SUM(n) / COUNT(n)`, а `COUNT(DISTINCT)` так просто не сложить.

**4. Почему ORDER BY ... LIMIT требует объединения результатов?**  
Каждый shard знает только свой локальный порядок. Глобально самые новые/большие строки могут лежать на любом шарде, поэтому нужно взять top-N с каждого, а затем отсортировать объединённый набор и обрезать до N. Без merge результат будет просто неверным: в нашем прогоне лучший заказ shard0 (`7403304`) оказался лишь 5-м глобально, а первым — заказ с shard2 (`9000003`).

**5. Что произойдёт при отказе одного shard?**  
Станут недоступны данные, привязанные к его shard key (≈1/N базы — у нас 32 884 заказа и 1 641 клиент). Запросы по этим клиентам начнут отдавать ошибку, распределённые — деградируют до частичного результата (`merged = 67 116` вместо `100 000` с пометкой `failed_shards = ['shard2']`). Остальные клиенты и остальные части сервиса продолжат работать, потому что данные независимы.

**6. Что такое hot shard?**  
Узел, на который приходится непропорционально большая доля нагрузки, хотя данных на нём может быть столько же. Причины: популярный tenant, неудачный ключ, неравномерный доступ, особый тип запросов. В нашем эксперименте строки были 33/34/33 %, а запросы — 40/21/39 %.

**7. Почему выбор shard key влияет на JOIN?**  
Join внутри одного узла возможен, только если связанные строки обеих таблиц попали на один шард. Если обе таблицы шардируются по одному и тому же ключу (например, `customer_id` для заказов и клиентов), их строки ко-локализованы, и join остаётся локальным. Если ключи разные, join становится cross-shard и уходит в приложение.

**8. Какие операции особенно плохо подходят для распределённых данных?**  
Cross-shard JOIN и агрегации с `DISTINCT`; глубокий `ORDER BY … OFFSET`; транзакции, затрагивающие несколько шардов (распределённых транзакций «из коробки» нет); глобальные уникальные ограничения; согласованный backup/restore; перебалансировка. Идеально подходят операции по одному shard key.

**9. Что произойдёт при изменении количества shard'ов?**  
Часть ключей изменит шард, и данные придётся физически перенести. Объём зависит от стратегии: `hash % N` переносит почти всё (у нас 76.1 %), consistent hashing — примерно `1/N_new` (24.7 %). Перенос требует чтения и записи через сеть, поэтому его делают контролируемыми этапами, а не за один шаг.

**10. Чем шардирование отличается от репликации?**  
Шардирование (лаб. 5) делит **разные** данные между узлами: каждый шард содержит свою часть, вместе — целое. Репликация (лаб. 4) хранит **одни и те же** данные на нескольких узлах: Primary принимает запись, Replica воспроизводит WAL и обслуживает чтение. Шардирование повышает ёмкость и масштаб записи, репликация — отказоустойчивость и масштаб чтения. Их комбинируют: у каждого шарда есть своя реплика.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?**  
Да — но только single-shard запросы. Каждый шард хранит `1/N` данных, индексы меньше, кэш эффективнее, поэтому `WHERE customer_id = ?` становится быстрее (у нас 37 ms на 33k строк вместо выборки из 100k). Distributed запросы при этом **не** ускоряются, а иногда замедляются: нужно опросить все узлы, собрать и объединить результаты.

