# Часть A. Экспериментальная таблица `events`

```sql
CREATE TABLE events (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL,
  event_type VARCHAR(50) NOT NULL,
  payload JSONB,
  created_at TIMESTAMP NOT NULL
);
```

Контрольные объёмы: **10k → 100k → 1M → 5M** (10M не гоняли — места/времени хватило на 5M).

---

## Задание 3. Размер таблицы

| Количество строк | Размер таблицы | Общий размер (с PK) |
|------------------|----------------|---------------------|
| 10 000 | 672 kB | 944 kB |
| 100 000 | 6672 kB | 8912 kB |
| 1 000 000 | 65 MB | 87 MB |
| 5 000 000 | 326 MB | 433 MB |

После всех вторичных индексов на ~5.2M строк: таблица **339 MB**, всего с индексами **749 MB**.

**Вывод:** размер растёт почти линейно. Индексы на больших объёмах занимают сопоставимый (или больший) объём, чем сама таблица.

---

## Задание 4. SELECT без индекса

```sql
EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 123;
```

| Строк | Scan | Actual Rows | Rows Removed by Filter | Execution Time |
|------:|------|------------:|-----------------------:|---------------:|
| 10 000 | Seq Scan | 0 | ~10k | **2.2 ms** |
| 100 000 | Seq Scan | 0 | ~100k | **26.5 ms** |
| 1 000 000 | Parallel Seq Scan | 13 | ~1M | **142.6 ms** |
| 5 000 000 | Parallel Seq Scan | 59 | ~5M | **867.5 ms** |

*(На малых объёмах `user_id = 123` мог не попасть в random — время всё равно отражает полный проход таблицы.)*

**Вывод:** без индекса время SELECT растёт вместе с таблицей (~линейно). На 5M уже почти секунда на простой lookup.

---

## Задание 5. Тот же SELECT с индексом

```sql
CREATE INDEX idx_events_user_id ON events(user_id);
```

| Объём | Без индекса | С индексом | Разница |
|------:|------------:|-----------:|---------|
| 100 000 | 26.5 ms (Seq) | **0.17 ms** (Bitmap) | ~150× |
| 1 000 000 | 142.6 ms (Seq) | **0.35 ms** (Bitmap) | ~400× |
| 5 000 000 | 867.5 ms (Seq) | **1.0 ms** (Bitmap) | ~850× |

1. План: Seq Scan → Bitmap Index Scan + Bitmap Heap Scan, появляется **Index Cond**.  
2. Время падает на порядки.  
3. Разница заметна уже со 100k, на 5M — драматическая.  
4. Индекс **не всегда** оптимален: если нужно 30–50%+ таблицы, Seq Scan может быть дешевле.

---

## Задание 6. Диапазон по дате (на 5M)

`WHERE created_at >= NOW() - INTERVAL '1 day'` (~13.6k строк, малая доля):

| | Scan | Execution Time |
|--|------|---------------:|
| Без индекса | Parallel Seq Scan | **2402 ms** |
| С `idx_events_created_at` | Bitmap Index/Heap | **596 ms** |

Индекс хорошо режет узкий диапазон. Если запрос вернёт большую часть таблицы (год и больше при равномерных данных), PostgreSQL снова уйдёт в Seq Scan — читать кучу по индексу дороже sequential read.

---

## Задание 7. Фильтр + сортировка + LIMIT

```sql
SELECT * FROM events WHERE user_id = 123
ORDER BY created_at DESC LIMIT 100;
```

| | План | Time |
|--|------|-----:|
| До | Bitmap по `user_id` + **Sort** | 4.3 ms |
| После `(user_id, created_at DESC)` | Bitmap по составному + **Sort** | 3.0 ms |

У `user_id = 123` всего ~59 строк — Sort дешёвый, планировщик его оставляет. Порядок колонок важен: сначала равенство (`user_id`), потом сортировка (`created_at`). На пользователях с тысячами событий Sort обычно пропадает.

---

## Задание 8. Агрегация (5M, 30 дней)

```sql
SELECT event_type, COUNT(*)
FROM events
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY event_type;
```

План: Bitmap по `created_at` → HashAggregate / GroupAggregate.  
Обработано ~**411k** строк за 30 дней.  
Execution Time: **1863 ms**.

Индекс на `created_at` помогает отсечь период, но **не убирает** необходимость читать и группировать сотни тысяч строк. Один индекс не делает `GROUP BY` «мгновенным».

---

## Задание 9. Стоимость INSERT (по 100k строк, таблица уже ~5M)

| Состояние | Время INSERT 100k |
|-----------|------------------:|
| С тремя вторичными индексами | **10 567 ms** |
| Только PK | **876 ms** |

Индексы замедлили запись примерно в **12 раз**: каждая новая строка обновляет все индексы.

**Почему нельзя индексировать все колонки:** место на диске + медленные INSERT/UPDATE/DELETE + лишняя работа планировщика.

---

## Задание 10. Размер индексов (на 5M)

| Индекс | Размер |
|--------|--------|
| `idx_events_user_created` | 150 MB |
| `idx_events_created_at` | 107 MB |
| `events_pkey` | 107 MB |
| `idx_events_user_id` | 34 MB |

При росте строк индексы растут почти линейно и суммарно могут превысить размер таблицы.

---

## Задание 11. Когда индекс уже не спасает

Запрос вида `GROUP BY DATE(created_at)` за год на 100M строк:

1. Даже с индексом по `created_at` нужно прочитать/агрегировать огромный объём (десятки–сотни миллионов tid’ов и значений).  
2. Обрабатывается по сути весь годовой срез, не «одна страница».  
3. Индекс ускоряет поиск, но не убирает работу по агрегации и I/O.  
4. Дальше: партиционирование по времени, materialized view / rollup, OLAP, ограничение периода в API, архивация старых данных.

## Задание 13. Три запроса

2. **Диапазон дат:** `WHERE created_at >= NOW() - INTERVAL '7 days'`

## Задание 17. Узкое место

Сильнее всего от роста зависит запрос с **широким результатом** — status + период:

```sql
SELECT * FROM shop_order
WHERE status = 'PAID'
  AND created_at >= NOW() - INTERVAL '30 days';
```

| Объём | Строк результата | Time |
|------:|-----------------:|-----:|
| 100k | ~2k | 3.9 ms |
| 1M | ~20k | 47.5 ms |
| 5M | ~102k | **882 ms** |

Проблема: индекс находит нужные tid’ы, но потом надо прочитать **~43k heap blocks**. Индекс есть, а время всё равно растёт с объёмом выборки.

Лента клиента с LIMIT 50 почти не деградирует (5.5 ms) — читаем только хвост индекса.

## Задание 18. Улучшение

На 5M сравнили **без** индексов лабы 1 и **с** ними:

| Запрос | Без индексов лабы | С индексами |
|--------|------------------:|------------:|
| 7 дней по дате | Seq Scan **2481 ms** | Bitmap **2052 ms** |
| PAID + 30 дней | Seq Scan **1382 ms** | Bitmap **882 ms** |
| Лента LIMIT 50 | Bitmap FK + Sort **2.7 ms** | Index Scan **без Sort**, 5.5 ms |

Индексы помогают (особенно убирают Seq Scan и Sort), но на срезе ~100k строк всё равно сотни миллисекунд–секунды. Дальше: обязательный узкий `from_date` в API, партиции по `created_at`, архив старых заказов.

## Задание 19. Граница применимости индексов

На `events` при **5M**: lookup без индекса ~**870 ms**, с индексом ~**1 ms** — точечный SELECT индекс ещё спасает.

Но агрегация за 30 дней ~**1.9 s**, INSERT 100k с индексами **~10.5 s** vs **~0.9 s** без них.

На `shop_order` при **5M**: запрос PAID за 30 дней с правильным составным индексом всё равно **~0.9 s**, потому что возвращает ~100k строк. С 100k до 5M время выросло с **4 ms до 882 ms** при том же типе плана.

**Формулировка:**  
При объёме около **5 млн** заказов точечная лента клиента с LIMIT остаётся быстрой (~5 ms), а «все PAID за месяц» занимает около **1 секунды** даже с индексом `(status, created_at)`. Индекс убрал Seq Scan, но не остановил рост стоимости с объёмом результата. Для такого сценария одних индексов недостаточно — нужны ограничение периода, партиционирование или предагрегация.

## Контрольные ответы (кратко)

1. Seq Scan ок, если нужна большая доля таблицы.  
2. Индекс могут не взять из‑за низкой селективности / статистики / стоимости.  
3. INSERT обновляет все индексы строки.  
4. Много индексов = дорогая запись.  
5. Селективность — доля строк, подходящих под условие.  
6. Маленькая доля → индекс читает мало страниц.  
7. Большая доля → random I/O индекса хуже sequential.  
8. EXPLAIN ANALYZE — реальные время и строки.  
9. Rows Removed by Filter — отсеяно после скана.  
10. Index Cond — условие, применённое в индексе.  
11. Index Scan — по одному; Bitmap — bitmap tid’ов, потом heap пачками.  
12. Порядок колонок = left-most prefix.  
13. GROUP BY всё равно читает и агрегирует много строк.  
14. Статистика (`ANALYZE`) влияет на выбор плана.  
15. С ростом таблицы растут I/O, время Seq Scan и размер индексов.  
16. Индексы на всё — диск + медленная запись.  
17. `pg_relation_size` / `pg_size_pretty`.  
18. То же для `indexrelid` в `pg_stat_user_indexes`.
